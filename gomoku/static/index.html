OpenJev 五子棋竞技场

JEV 决策服务 大模型服务

JEV 是怎么下五子棋的？

JEV 使用 APUS-OpenJev-v1（9B）。它不是聊天模型，而是决策模型：给它“局面 + 任务 + 2~16 个候选”， 它只对候选打分，返回选中的候选和每个候选的概率，不会自由生成文字。所以 JEV 下棋采用“算法提名，模型拍板”的方式。

一步棋的流程

① 候选生成算法按棋型评分（进攻 + 防守）从空位中选出前 10 个候选点
→
② 战术描述给每个候选写出“进攻效果 / 防守效果”，例如“形成活三”“堵住对手成五”
→
③ 组装请求state：ASCII 棋盘 + 最近落子 + 双方威胁摘要；instructions：优先级规则
→
④ 模型打分候选被标成 A~J，OpenJev 在答案位置只比较这些标签的 logits，softmax 得到概率
→
⑤ 投票落子打乱顺序再问一次，两次概率取平均，选概率最高的点

为什么要这样设计

设计原因
由算法提供候选模型一次最多只能在 16 个选项里选，且只能选择不能生成坐标；这样也保证每一步都合法。
候选附带战术描述 + 威胁摘要模型从文字理解局面比从棋盘图“看”几何关系可靠得多；初版只有简单描述时，对简单算法仅 2:18。
打乱候选顺序避免模型直接沿用算法排序，让决策真正来自模型。
两次投票取平均测试发现模型偏好某些字母位置（如 C），换顺序平均可以抵消这种偏置。
effort：high / lowhigh 执行全部 32 层；low 在第 16 层提前退出、只投影候选标签，更快但更弱（下棋时漏堵明显）。

发送给模型的请求（示意）

{
  "state": "Gomoku ... 15x15 board ...\n    A B C D E ...\n15  . . . ...\n...\nIt is Black's (X) turn.\n
            Threat analysis: Opponent has an open three: they make an open four at G5, K9 ...",
  "instructions": "You are Black (X). Choose the strongest next move. Priorities: 1) WIN ... 2) BLOCK five ...",
  "criteria": [
    {"id": "G5", "description": "Play X at G5. Attack: builds an open two. Defence: blocks the opponent's open-four point."},
    {"id": "G8", "description": "Play X at G8. Attack: creates an open three. Defence: no defensive effect."},
    ...
  ],
  "effort": "high"
}
→ {"choice": "G5", "probabilities": {"G5": 0.61, "G8": 0.27, ...}, "executed_layers": 32}

实测表现
